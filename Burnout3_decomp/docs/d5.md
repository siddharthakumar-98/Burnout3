## Step 1: `tools/bo2map.py` (2026-10-08)

Spec `docs/superpowers/specs/2026-10-08-bo2map-design.md`, plan `docs/superpowers/plans/2026-10-08-bo2map.md`.
`tools/bo2src.py` reads a [b3dllc/burnout2](https://github.com/b3dllc/burnout2) checkout (kept outside the repo):
its game functions (bodies found under the `// 0xSTART - 0xEND` comments in `src/gamesource`, `src/GameShared`,
`src/nodebug`; 1,899 functions), the names their bodies call, their string and float literals, and vtable slot order
from `include/types/*.h` (inherited slots resolved). `tools/bo2map.py` pairs them with Burnout 3 game functions:
seeds (our adopted names, unique shared strings/floats, vtables whose slot sizes fit one class by a clear margin),
then link order (global address order, so our unit cuts don't box it in), vtable slots, callees and callers, to a
fixpoint. Tests: `python3 tools/test_bo2map.py` (12, synthetic). Run: `python3 tools/bo2map.py --bo2 PATH` (2.3 s),
`--unit UNIT`, `--eval`.

First run (138 rows): high 42, medium 37, low 59 (35 conflicts).

- Hold-out check (`--eval`): with one unit's names removed at a time, `d4/fs` comes back 16/17, `d4/pool` 0/8 and
  the load queue 0/4 (islands: nothing else anchors them); **0 wrong**.
- Spot check: all 13 non-seed `high` rows are consistent with Burnout 2's bodies (callees line up, e.g.
  `viBufCreate` → `viBufReset`, `CGTFilePS2DVD::Open` → `BuildFileName`/`GetFileNameFromDeviceName`, `CGame::Init`
  → `SetAsDefaultFilesystem`/`InstallToRenderWare`).
  - `unit_001D2EE0` = `CGTFileSystemPS2DVD`/`CGTFilePS2DVD`.
  - `unit_003248F0` = `CGTMpegManager`/`CGTMpegDecoder` + `viBuf*` (`vibuf.c`).
  - `func_001D41E0` = `CGame::Init`.
- `medium` rows are mixed (e.g. `COnePlayerCRASH::Update` proposed inside the force-feedback unit); treat them as
  leads to verify, not names.
- Why coverage is modest: Burnout 3 retail kept few strings (253 game functions reference any; 6 shared with Burnout
  2, 2 unique on both sides), 11 unique shared `.lit4` floats, and only ~70 named game functions to seed from. Sizes
  alone don't discriminate (8-byte stubs fit anything). Coverage grows with every unit we name: re-run after naming.
- Side finding: the tool also pairs unnamed kernel calls (`viBuf*` call `0x10BE40`/`0x10BE60` where Burnout 2 calls
  `WaitSema`/`SignalSema`; `0x114E60`/`0x114EB8` ↔ `DIntr`/`EIntr`). Vendor names are out of scope here.

## Completion (2026-10-08)

**D5 is closed under the roadmap's tail policy: 51 of 61 lifecycle/helper functions match exactly, with ten
recorded unmatched functions below.** Boot, the top-level frame/state machine, loading, shutdown and the five
embedded modes now have C++ bodies and shared layouts. Sixteen D5 functions are linked. Units containing a tail
function still link their original assembly; this is milestone closure, not a claim of 100% game decompilation.

The public report is **129 / 5,654 game functions (2.28%)**, **20,096 / 2,674,804 code bytes (0.75%)**; **82 functions
in 26 C/C++ files are linked**. Vendor libraries are outside that denominator. The Phase 1 gate still requires every
game function to match and link, including the D4/D5 tails.

D5 covers mode lifecycle and loading. The rendering callbacks at `0x134A20`, `0x134DF0`, `0x1354E0`, frontend draw
`0x1312D0`, and preview rendering/geometry/input at `0x24D520`–`0x24FC20` remain D6/D10 work. The standalone audio
setup/volume routine `0x130EE0` belongs to D10's audio/EA Trax integration: its callers are `0x31CF30`, `0x424480`
and `0x453EA0`, not the frontend stage loader. Its C draft and the frontend drawing draft are retained in
`frontend_flow.cpp`, but are excluded from D5's ten-function tail. This follows the existing D10 scope; these game
functions remain in the public progress denominator.

## Layout and state-machine findings

`func_0012EB30` initializes `D_004EE040`, polls `func_00133190` until loading completes, runs `func_00132600` until
exit, then calls `func_00132560` and `func_00132420`. The game-object unit really ends at `0x134260`; the startup
helper unit ends at `0x131CE0`, before the already linked D2 function.

`Game` in `game.h` contains `CAsyncLoadManager` at `+0x80C0`, per-frame subsystems at `+0x28E00`/`+0x299B0`, and
five embedded modes initialized by `func_00133BB0`:

| Offset in Game | Mode |
|---|---|
| `+0x2C668` | frontend/movie |
| `+0x2C9A0` | model preview (yaw/pitch and geometry controls; not an established Crash-mode identification) |
| `+0x2CCC0` | single-player |
| `+0x2CE80` | two-player |
| `+0x2D048` | network |

The current-mode pointer is `+0x2DA48`; **`+0x2DA4C` is the next-mode pointer**, not an integer state. Next/current
state words are `+0x2DA8C`/`+0x2DA90`. Typing that pointer correctly made the network update match exactly.
The main-loop body now includes state dispatch, driver updates, pause/reload transitions, loading services,
frame timing and per-frame status clears. Init remains a 100% match.

The shared mode prefix has scene/player/opponent/traffic hashes and type arrays, three counts at `+0xA0`–`+0xA8`,
vptr at `+0x1B0`, target at `+0x1B4`, auxiliary target at `+0x1B8`, and reload flag at `+0x1BC`. The earlier blanket
claim that `unit_00134570` could not contain base-mode code was too broad: its first eight default stubs
(`0x134570`–`0x134600`) are shared with physics/object vtables, but **`0x134600`–`0x134930` are shared mode lifecycle
helpers**. The two-player vtable at `0x4DDD90` refers to the methods at `0x13C940`.

Network reset clears eight client-enable bytes at InputRoster `+0xB080`, stride `0x4F20`. Using that parent object
and offset recovered the original relocation and made the reset match. Frontend audio handles are arguments to
`0x386010`/`0x386240`; volume bytes are signed. Movie decoding uses the exact NTSC `1/29.97` constant, while the
PAL frame interval is `0.04`.

## Reuse and validation

Burnout 2's recovered `CGameMode` hierarchy, debug types, and corresponding lifecycle bodies were checked first,
using `bo2map.py` and the external checkout inspected at `61e466e`. They guide the shared lifecycle/vtable model;
Burnout 3's larger/reworked modes require offsets and control flow checked against Ghidra and the original listing.
Keep anonymous `func_` names where a one-to-one Criterion name has not been established. Dependency interfaces
continue to use [the existing library references](library-references.md); no vendor source replacement was needed.

A D5 matching audit found `litfix.py` could silently substitute a different float when draft instruction offsets
moved. It now compares the source literal's four bytes with loads from the original function's immutable pool,
chooses only an equal value, and clears any resolved relocation addend. Unverified values retain their original
relocation with a warning. This caught the `1/30` versus `1/29.97` movie constant and preserves PAL/NTSC distinctions.
