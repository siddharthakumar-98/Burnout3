# D4: core infrastructure

D4 decompiles the code everything else stands on: memory, math, file I/O and streaming, the tuning system
(`Data/vdb.xml`) and strings/localization. This file is the map: which units hold each subsystem, the evidence, and the
order to work in. Addresses are VRAM; units are the provisional ones in `../assembly/splat/b3.yaml`
([layout.md](layout.md#game-translation-units)). Found with Ghidra through ghidra-mcp (decompiler, callers) and
`tools/xref.py`.

**State:** D4.0 (tooling), D4.1 (library names) and D4.2 (this map) done; D4.3, decompiling, is under way
([progress](#progress)). The map below is corrected as the evidence comes in.

## What D4.0 and D4.1 set up

- **Ghidra mirrors the repo.** `tools/ghidra_sync.py push` creates the functions Ghidra's analysis missed (1,336 of
  them, mostly reached only through pointers), applies the repo's names and tags every function with its unit
  (`unit:game/unit_…`); `pull` lists names given in Ghidra for review; `status` compares the two. After a push, pull
  reports nothing, so the round trip is clean. Remaining differences are expected: libkernl's kernel patches stored
  as code in `.data` (9 Ghidra functions) and one hand-written RenderWare routine at `0x1FFFD8` that Ghidra has typed
  as data (select it, press C, then F).
- **Three functions were invisible to our tools.** spimdisasm emitted `0x1060F8`, `0x21AC70` and `0x376570` as
  `.word` data. Ghidra showed they are called functions; `config/symbol_addrs.txt` now declares them, so they count
  as functions (their bodies still print as `.word`).
- **257 library functions are named** in `config/symbol_addrs.txt`, which splat uses for the generated assembly:
  - 138 libkernl syscall stubs (`0x10BA00`–`0x10C290`), names from ghidra-emotionengine-reloaded's syscall table,
    checked against PCSX2's;
  - 66 functions named by their own messages (`sceDbcSendData`, `lgAudInit`, `lgDevRead`, DirtySock's
    `_LobbyStatbookViewCb`…), found by `python3 tools/xref.py names`;
  - 24 newlib functions (`memcpy`, `memset`, `str*`, `sprintf`, `printf`, `malloc`/`free`, `vfprintf`…) and 29 libgcc
    functions (`__muldi3`, the `__divdi3` family, soft-float), read in Ghidra.
  - CodeWarrior calls soft-float helpers by its own names; the three that game code uses are linker aliases in
    `config/linker_extra.ld` (`dptoli` → `__fixdfsi`, `dptofp` → `__truncdfsf2`, `fptodp` → `__extendsfdf2`).
- **The game hardly uses newlib's allocator** (one `malloc` and one `free` call). It has its own heaps and pools
  (below).
- **Inline VU0 assembly compiles.** CodeWarrior 3.0.3 accepts MW-style `asm { vsub.xyzw vf1, vf0, vf0; sqc2 vf1, 0(p) }`
  inside C functions, with C variables as operands, and whole `asm` functions; it schedules those instructions like
  its own. See [compiler.md](compiler.md#inline-assembly-d4).

### Memory
| Where | What | Evidence |
|---|---|---|
| `unit_003E7850`, `unit_003E7AD0`, `unit_003E7D40` (`0x3E7850`–`0x3E8DD0`) | Heap core | `0x3E7850` allocates and `0x3E7AD0` frees by block type (switches through jump tables at `0x4CAE30`/`0x4CAE90`); `0x3E8B70`/`0x3E8BA0` allocate and free from sub-heaps. |
| `unit_00222300` (`0x222300`–`0x222C90`) | Memory manager: allocation by category | A class: its seven methods are exactly vtable `0x4DE030` (`0x222300` alloc, `0x2223B0`, `0x2223C0`, `0x2224C0`, `0x2225C0`, `0x222620` free, `0x222650` init), and `__sinit` #18 installs that vtable in the one global instance at `0x1D6D880` (`0xA00` bytes). | `unit_002B6C40` (`0x2B6C40`–`0x2B6FF0`) | Fixed-size pool (free list) | Two structs. Pool: `+0` base, `+4` stride, `+8` count, `+0xC` alignment, `+0x10` free list; `0x2B6EF0` init (pool, count, element size, alignment, initial contents, buffer), `0x2B6EC0` buffer size (`count × align(size + 8) + align`), `0x2B6E20` rebuild the free list in address order. List: `+0` pool, `+4` used list; `0x2B6E10` init, `0x2B6DA0` alloc, `0x2B6CA0` free, `0x2B6C40` free all, `0x2B6D20` move between lists. Nodes carry an 8-byte header (next, prev). |
| `unit_001D4680`, `unit_00383C10` | Pool users | `0x1D4680` creates pools; `0x1D7580`/`0x1D7560` (called from 56 and 49 units) allocate and free a pooled object by index. |

### Math and VU0
There is no central math library in the game code: VU0 macro instructions are inlined into their callers (`0x1AB010`
zeroes five vectors), the way inline methods of a vector class compile. Out-of-line copies exist where an address is
needed: `0x130BF0`, a vector constructor that clears `w`, is what `__construct_array` calls for arrays of vectors in two
static initializers. The game also
calls RenderWare's math (`rw/renderware`, D11). So D4's math work is a header of inline VU0 operations
(`c_cpp/include/vu0.h`), grown from the first functions that need it, rather than a unit of its own.

### Tuning (`Data/vdb.xml`, the "ValueDB")
`Data/vdb.xml` is not XML: it is a binary table the tools exported from `.cfg` files (`../export/ValueDB/...`), read
whole into the database object and looked up by key. Format and hash are in `tools/vdbhash.py`, which checks them
against your own copy of the file (local only): **439 of the 442 registrations** whose strings are visible in the code
resolve in the shipped file; the three that don't (`Low Detail ESM 2 player gain`, `Lost/Gained Boost Segment Gain`)
keep their defaults.

| Where | What | Evidence |
|---|---|---|
| `0x21B8C0`–`0x21C010` (first 8 functions of `unit_0021B8C0`) | Variable registry | `0x21B8C0` init (db object in `.sbss` `0x4E2920`); `0x21B9B0`/`0x21BB60`/`0x21BD80` register a vector/float/int variable: they hash `name + group + "/" + cfg` with `0x21BFA0`, fill a 32-byte entry (+0 destination, +4/+8 max/min, +0xC/+0x10/+0x14 the three strings, +0x18 key, +0x1C count, +0x1D flags, +0x1E type: 1 int, 2 float, 3 bool, 5 vector) and apply the value at once. The hash is CRC-32's loop over the standard table (`.data` `0x49B110`, this file's) from `0xFFFFFFFF` with no final inversion, but with an arithmetic shift and signed characters. `0x21C010` onward calls track/race code and is another file. |
| `unit_0024FDE0` (`0x24FDE0`–`0x250160`) | The database class (vtable `0x4DE0F0`) | `+0x14` `0x24FDE0`: is a `.cfg` in the file (binary search of the file table by `hash(cfg)`); `+0x10` `0x24FFC0`: apply one entry (binary search of the value table by key, copy by type, `memcpy` for arrays); `0x24FE90`: point at a newly loaded file's tables and re-apply every live entry; `0x250120`: init (entry table at `+0xC20`, `0x6C8` entries); `+0xC` `0x250100`: unregister (`0x21B8F0`). `0x250160` is unrelated VU0 code called from `0x1ADA00` and belongs to another file. |
| `unit_0021B5E0` (`0x21B830`) | Loader, in the options file | Opens a path through the file system, reads it into the object at `+0xE540` rounded up to 2 KB, calls `0x24FE90`, closes. Its neighbours apply option settings (`0x21B5E0`). |

## Unit boundaries

Decompiling a unit needs it to be one file. Step 1 settled these; each cut is in `FORCED_CUTS` or `MERGES` in
`tools/tusplit.py` with its reason, and the data slices were regenerated with them. Static initializers are numbered by
their position in `.ctor`, from 0.

- **`unit_002B52C0` was four pieces.** `0x2B52C0` is RenderWare Audio's (a callback that `0x2B51F0` takes the address
  of, sharing `.sbss` `0x4E2CF4`), so `rwa/` now ends at `0x2B52D0`. `0x2B52D0`–`0x2B6C40` is game code driven from
  `unit_0015F270` (it calls back into it), not RenderWare Audio. The pool starts at `0x2B6C40`: `0x2B6BC0` initializes a
  different struct and is called from `unit_0015F270`, and `0x2B6C30` is a `return 1` stub left with the code before.
  `0x2B6FF0`–`0x2B7110` are request accessors, not event-flag helpers: `0x1A84A0` posts a request object (type at
  `+3`, a 16-bit id at `+0xC`, pending flag) and `0x1A8540` cancels one. Several other files end with the same
  get/post/cancel triples, all cancelled from `0x23F860`.
- **`unit_0012EB30` was four files.** `main` alone; input wrappers `0x12EEF0`–`0x130030` (one struct: `0x12FFB0`, the
  constructor, and `0x12EEF0` both store the frame counter at `+0x128`, which settles `0x12FFB0`–`0x130030`); debug
  drawing `0x130030`–`0x130C20` (a stroke font in `.data` `0x487C40`–`0x488050`, a line batcher, a `%.03f` readout;
  the first `__sinit` builds its line buffer); and the movie/boot class `0x130C20`–`0x131AA0`. There is no video code:
  the movie names belong to the last file. The large `.sdata`, `.sbss` and `.bss` slices went with the files that use
  them (`.bss` `0x4ED7E0` to debug drawing, `0x4EDFF0`–`0x4F5080` with the `0x4EE040` object to the class), not to
  `main`, which owns only its strings.
- **`unit_002220E0`.** The "RenderWare hooks" (`0x2220E0`–`0x222300`) are the constructor, destructor and static
  callbacks of the class whose methods are at `0x221420`–`0x2220E0` (instance `0x67D640`), so they rejoin
  `unit_0021B8C0`; the old cut came only from separating `__sinit` #17 and #19. The memory manager is exactly
  `0x222300`–`0x222C90`. `0x222C90`–`0x22B850` is one file (`__sinit` #19 fills the const vectors at `0x4B9DA0` that
  `0x223130`, `0x225440`, `0x2284B0` and `0x2298B0` read). `0x22B850`–`0x22D2E0` is a controller layer, merged with
  the former `unit_0022BEE0`.
- **`unit_001AB120`** (`0x1AB120`–`0x1D2EE0` now) lost its last two files, the `dvd:` device and the boot/system file
  with `language=%d` (above). Its `.rodata` cut before the device is not exact: the device's one item (`0x4B7DE8`)
  follows a float table of `0x1D0F50`'s with no 16-byte boundary between them, so that table sits in the device's
  slice for now.
- **`unit_00217070`** is pad code, not resources. With its neighbours `0x216E40`–`0x217070` it is one class (vtable
  `0x4DDFF0`, installed by `__sinit` #1 in the controller objects): stick dead zones and pressure curves for the read
  in `0x214CD0` (libpad2), vibration through libdbc (`0x217070`, `sceDbcSendData2`). Merged into `unit_00216E40`
  (`0x216E40`–`0x217610`) and tagged `subsystem:pad` in Ghidra, with `0x214CD0`. `0x217610`–`0x217850` is a base class shared by four unrelated vtables (virtual forwarding,
  an interface lookup by 64-bit id).

Still open in `unit_001AB120` (196 functions; every gap is crossed by some link): classes with their own vtables at
`0x1AB6B0`–`0x1AC470`, `0x1BAAF0`–`0x1BDE50`, `0x1BDF60`–`0x1BE250` and `0x1CBA30`–`0x1CE470`; a vtable whose
methods are at both `0x1BEA60` and `0x1D2790`–`0x1D2C10`; `__sinit` #12 at `0x1C8870`–`0x1CC4C0`; the `HEVYCAR*`
strings shared by `0x1BF580` and `0x1C6600`; and the weakest gaps at `0x1AB610`/`0x1AB6B0` (one link), `0x1D0B50`,
`0x1D1670` and `0x1D2D70`. To split when its code comes up.

## Order of work

1. **Strings (`unit_002130F0`).** 14 small functions with no calls into other game code: the first whole unit to
   match and link, with its `.rodata`/`.sdata` slices.
2. **Memory.** The pool (`unit_002B6C40`), then the heap core and the memory manager (`unit_00222300`).
3. **File system.** `unit_002127A0`/`unit_002129A0`, then the load queue. These are C++ classes, so they settle how
   classes, vtables and their RTTI are written (`.vtables` is one piece today).
4. **Tuning.** The `vdb.xml` loader, parser and variable table, including the key hash.
5. **Math.** `vu0.h` grows with each of the above; small VU0 functions such as `0x130BF0` come along when their
   units are reached.

## Progress

Steps of D4.3, one commit each.

0. **Hand-set boundaries survive regeneration.** `tools/tusplit.py` has `FORCED_CUTS` (always a boundary, never
   merged away) and `MERGES`, and `tools/dataslice.py` has `FORCED_CUTS` for slice starts; each entry carries its
   reason. Both tools treat `d4/` units as carved. Before any new entry, regenerating gave back `b3.yaml` exactly except
   for one hand-set slice start, libc's `.data` at `0x4873F0` (newlib's `impure_data` follows it, with no direct code
   reference); it is now the first data `FORCED_CUTS` entry.
1. **Unit boundaries** ([above](#unit-boundaries)): 11 forced cuts and 6 merges in `tusplit.py`, one more forced
   `.bss` slice start in `dataslice.py` (after the memory manager's heap object), and RenderWare Audio's end moved to
   `0x2B52D0`. Hand-set boundaries now count before the initializer anchors, so an anchor forces a cut only where
   nothing else separates two initializers. 363 units (was 358).
2. **Compiler, then strings.** Every function in C was compiled under all 19 `3.0.x` builds: **3.0.1 build 119** is
   best or equal best on all of them, and the build now uses it ([compiler.md](compiler.md#build-119-d4)); it also
   settled `-O3` vs `-O4` and brought the D2 near-misses `func_00131CE0` and `func_0013AE70` to 100% (linked).
   `d4/ustring` (carved from `unit_002130F0`; its data is `ConvertUTF.c`'s tables, a `powersOf10[10]` float table and
   four 2-character `u16` strings) is at 12 of 14: `ustrFromFloat` (89.9%) and `ustrFromFloatNoSep` (91.7%) remain,
   so the unit is not linked yet. `d4/ustrfmt` (`0x212E30`–`0x2130F0`, `%1`–`%4` substitution) is linked.
3. **Memory.** `d4/pool` (8 functions) is linked. The heap core (`c_cpp/src/d4/heap.c`, one source file for the three
   asm units `unit_003E7850`/`unit_003E7AD0`/`unit_003E7D40`, which are cut at its jump tables) is at 9 of 13:
   `func_003E7850` and `func_003E7AD0` differ only in relocation names (jump-table and branch labels), like
   `func_0014EC30`; `func_003E7D40` (91.6%, 2.5 KB, case order) and `func_003E8C20` (98.7%, the order of the return
   blocks of a 36-value compare chain: tried `if`/`else` with a result variable, `switch`, `?:`) remain. The memory
   manager (`unit_00222300`) is not started.
4. **File system.** `.vtables` is cut into per-unit slices (`tools/dataslice.py`: each vtable goes with the unit
   that defines its own methods; they are in link order with one exception, the pointer to `_start` at `0x4E0610`,
   which is a piece of its own). The file system is one unit (`unit_00212580`, see the map) and `d4/fs`, 18
   functions in C++, is linked. Its data stays in assembly for now: fopen's mode strings are 8 bytes apart in the
   original while CodeWarrior gives each literal a 4-aligned 2-byte section, and `"r"` (`0x4B96D8`) lies in the
   slice before this unit's because slices are cut at 16-byte boundaries. The load queue (`unit_0013C940`) is in
   progress.
5. **Tuning.** Format and key hash solved (`tools/vdbhash.py`, see the map). `d4/vdb` (registry, 8 functions) and
   `d4/valuedb` (the database class, 6 functions, with its vtable defined in C) are linked. The options file with
   the loader (`unit_0021B5E0`, `c_cpp/src/d4/options.cpp`) is at 4 of 5: `func_0021B5E0` (92.3%) copies two flags
   with an idiom not reproduced yet (the original normalizes each to 0/1 with `movz` against a hoisted 1, then
   tests `== 1`; best variant `int on = 1; if (!x) on = 0; ... = on == 1;` at 89.5%).
   Only C++ reproduces the virtual calls (through `$t9`; C function pointers go through `$v0`).

Matching ran through one subagent at a time (`.claude/agents/decomp-matcher.md`), each given at most about 8
functions and the evidence gathered so far, with `tools/funcmatch.py --all` for one-line-per-function status. Two
early runs in parallel that read whole units into context used about 8M input tokens each in 9 minutes; with the
budget rules a run takes 3-4 minutes and about 90k tokens.
